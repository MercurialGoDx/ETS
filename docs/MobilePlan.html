05CPU-оптимизация симуляции (Jobs/Burst — по замерам) делаешь самВпереди0/13

Делаешь сам — профилирование и Jobs/Burst. Шаги идут по возрастанию цены. Каждый следующий — только если профайлер на целевом телефоне после предыдущего всё ещё показывает узкое место. Полный DOTS/ECS — не делаем (переписывание врагов, оружий и эффектов статусов = новый проект).

Шаг 1 — дёшево, делаем всегда

  • не выполнено: Update-менеджер: один ISimulationTick (из DI) обходит массивы активных врагов/снарядов вместо сотен Update() (убирает накладные расходы native→managed вызовов). Регистрация — через пул (Фаза 4)
  • не выполнено: Высота рельефа без луча: SnapToGround (Enemy.cs) — Terrain.SampleHeight или запечённая карта высот вместо Physics.Raycast на каждого врага каждый кадр
  • не выполнено: Враги как кинематические тела, которые двигаются через transform: проверить цену синхронизации трансформов с физикой (autoSyncTransforms, коллайдеры) — особенно на x3
  • не выполнено: Проверка: мс/кадр скриптов врагов до/после в тестовом сценарии

Шаг 2 — анимация врагов (если узкое место — Animator/скиннинг)

  • не выполнено: Массовые враги без Animator: анимации запекаются в текстуру (VAT), проигрываются шейдером + GPU instancing; Animator остаётся только у боссов
  • не выполнено: Проверка: мс Animator + рендер скиннинга до/после, draw calls

Шаг 3 — Jobs + Burst (если скрипты врагов всё ещё > ~3–4 мс/кадр на целевом телефоне)

  • не выполнено: Пакеты com.unity.burst, com.unity.collections, com.unity.mathematics; проверить Burst в IL2CPP ARM64-сборке
  • не выполнено: Данные врагов (позиция, скорость, множители замедления, состояние) — в NativeArray, владелец — менеджер врагов; MonoBehaviour остаётся «представлением»
  • не выполнено: Движение и разворот — IJobParallelForTransform + TransformAccessArray; привязка к земле — карта высот в job или пачка RaycastCommand
  • не выполнено: Движение массовых снарядов (ракеты, отскоки) — тот же подход, если их сотни
  • не выполнено: (При тысячах врагов) пространственная сетка (spatial hash) в job для поиска целей и AoE вместо перебора EnemyManager.GetEnemiesInRange
  • не выполнено: Один sync point за кадр (Schedule в начале кадра, Complete перед использованием), без Complete() сразу после Schedule
  • не выполнено: Проверка: мс/кадр до/после, загрузка ядер в Profiler (Timeline), отсутствие регрессий геймплея (отбрасывание, замедление, оглушение, ледяная тюрьма)

  • выполнено: Платформа: только Android (2026-10-25: iOS исключён — платная подписка Apple Developer Program $99/год). Код остаётся без Android-специфики за пределами платформенных сервисов, так что к iOS можно вернуться позже без переделок.
  • выполнено: Ориентация: только landscape (Landscape Left/Right, autorotate между ними)
  • выполнено: Без монетизации (ни рекламы, ни IAP; UMP-согласие нужно только под аналитику)
  • выполнено: Только одиночная игра, без лобби/мультиплеера. Аудит: сетевого кода в проекте нет (Netcode/Lobby/Matchmaking отсутствуют), есть лишь пакет com.unity.multiplayer.center — удалить. Единственная онлайн-функция — таблица лидеров (асинхронная: отправка рекорда + чтение топа).
  • выполнено: Лидерборд — Firebase Auth (анонимный) + Firestore (утверждено 2026-10-25). Почему не Google Play Games: к записи GPGS можно приложить лишь scoreTag ≤ 64 символа, а наш BuildSnapshot — до 64 int → просмотр билда игрока (BuildViewerUI) потерялся бы. Firestore хранит снимок целиком, существующий UI лидерборда переиспользуется, Firebase всё равно в стеке.
  • выполнено: Firebase-модули: Analytics + Crashlytics + Remote Config + Auth + Firestore. Облачных сейвов нет.
  • выполнено: Addressables — только локальные группы (всё внутри билда). Удалённый каталог требует хостинга (CDN), версионирования каталога и даёт выигрыш только при частых контент-апдейтах без релиза — для нас не нужен. Ценность Addressables здесь — загрузка/выгрузка по требованию (память на слабых телефонах). Переход на удалённый каталог позже возможен без переделки кода (меняется только профиль групп).
  • выполнено: Достижений на мобилках нет. AchievementManager (Steam) живёт только в PC-сборке; на мобилках — NullAchievementService.
  • выполнено: Ветки (2026-10-25): mobile — основная ветка мобильной разработки. Фича-ветки создаются от mobile и мержатся в mobile. main заморожена на последнем PC/Steam-состоянии и больше не трогается (никаких merge в обе стороны). Подробно — docs/Git.md.
  • выполнено: Режим работы — обучение (2026-10-25): VContainer, UniTask, пулинг и профилирование, Addressables, Firebase пользователь внедряет сам. Claude объясняет: зачем это делаем, какие преимущества даёт, как сделать по шагам, на что смотреть при проверке — и формулирует, как это объяснить на собеседовании. Остальное (UI, ввод, ассеты, сборка) Claude может делать сам по согласованию.

Риски

  • Переход на asmdef может сломать ссылки на скрипты из AssetStore-пакетов → делать первым и отдельно.
  • DI-миграция затрагивает сотни мест → строго по одному сервису, с Play-проверкой после каждого.
  • Time.timeScale (x1/x2/x3/пауза) влияет на UniTask/DOTween — явно выбирать scaled/unscaled.
  • Firebase + IL2CPP stripping + EDM4U — частый источник проблем сборки → отдельная тестовая сборка сразу после подключения.
  • Firebase не для продакшна на Desktop → не включать в PC-сборку.
  • Jobs/Burst усложняют код (данные в NativeArray, sync points, отладка) и на телефонах дают меньше, чем на ПК (мало мощных ядер) → только по замерам, после Update-менеджера и VAT-анимации.
  • Лидерборд без серверной валидации взламываем (клиент пишет свой результат) → rules + проверки правдоподобности сейчас, серверная проверка — если читеры станут проблемой.
  • Бесплатный тариф Firestore (Spark): 50k чтений/день — кешировать топ (TTL ~1–5 мин), не перечитывать на каждое открытие.

Принципы миграции

  • Постепенно (strangler): каждая фаза оставляет игру играбельной на ПК; между фазами — Play-проверка.
  • Сначала инфраструктура и архитектура, потом мобильный UX — иначе новый UI придётся переписывать под DI.
  • Горячие объекты (враги, пули, VFX) не резолвим через DI поштучно — получают контекст через фабрику/пул (Init(...)), чтобы не платить за инъекцию на каждый спавн.
  • Всё платформенное — за интерфейсами с реализациями под PC/Mobile (+ Null-реализации для редактора/тестов).
  • Каждая фаза: refresh_unity(compile) + read_console(error) чисто, Play-тест, коммит.
  • Каждая фаза — своя ветка от mobile (feature/…, refactor/…), после проверки мерж в mobile.
  • Фазы с пометкой «Делаешь сам» — учебные: сначала объяснение (зачем / преимущества / как / вопросы с собеседований), потом реализация руками пользователя, Claude — ревью и помощь при ошибках.
