# Порт Endless Tower Survivors на Android

> Статус (2026-11-23): **играбельный порт в ветке `feature/android-port`**. Есть мобильный слой (сенсорное управление, экранные кнопки, лимит FPS, пауза при сворачивании, локальные рекорды), Android-настройки и сборка APK/AAB из меню `Tools/Android`. Архитектурные фазы (DI, UniTask, Addressables, Firebase) не начаты — см. «Порядок работ с 2026-11-23».
> Работу ведёт агент (Claude Code); где ниже написано «Codex» — та же роль.
> Стратегия: **один проект для Windows/Steam и Android**. Codex ведёт реализацию, замеры, тесты и сборки. Пользователь задаёт игровые приоритеты и получает объяснения по ходу порта.

## Разделение работы
- **Codex выполняет технический порт.** Пишет код, меняет настройки Unity, подключает пакеты, снимает и сравнивает замеры, тестирует, собирает приложения и ведёт RoadMap. Для Unity использует CLI/MCP.
- **Пользователь ведёт геймдизайн.** Уточняет приоритеты и принимает решения, которые меняют ощущение игры: например, подтверждение покупки, читаемость эффектов и допустимая точность восстановления боя. Технических заданий для пользователя больше нет.
- **Перед шагом** Codex записывает, что меняет, какую проблему решает и как проверит результат. **После шага** записывает, что получилось, что изменится для игрока, какие проверки прошли и что идёт дальше. Объяснение строится на поведении игры и результатах проверок. После запуска работ отдельная команда на каждый технический шаг не требуется.
- **Доступы и публикация.** Если для устройства, сервиса или Play Console нужен доступ владельца, Codex запрашивает его в момент, когда он понадобится. При доступном аккаунте Codex сам выполняет техническую настройку и готовит выпуск. Публичную публикацию согласовывает владелец продукта.

## Исходное состояние
- Игра на Unity 6000.0.80f1 и URP 17. Основная сцена — MainScene. На ПК используется Steam. Под Android настроен профиль сборки и получен первый Development AAB.
- Игровые сервисы частично связаны через синглтоны и поиск компонентов. Addressables уже используется через Localization, пулы работают для врагов и части игровых объектов. Сценарий x1/x3 и первые замеры показали рост затрат на создание объектов и выделения памяти в ускоренном бою.
- Полный геймдизайн текущей игры зафиксирован в `doc/Endless Tower Survivors GDD.doc`. Хронология подготовки и сырые показатели сохранены в архиве ниже и в `docs/Phase0Baseline.md`.

## Решения
- [x] **DI: VContainer** (утверждено 2026-09-29)
- [x] **Мобильная платформа: только Android** (2026-10-25). Платформенный код изолируем в отдельных сервисах, чтобы упростить возможный порт на iOS в будущем.
- [x] **Ориентация: только landscape** (Landscape Left/Right, autorotate между ними)
- [x] **Без рекламы и внутриигровых покупок.** Условия сбора данных проверяются перед подключением аналитики.
- [x] **Только одиночная игра, без лобби/мультиплеера.** Аудит: сетевого кода в проекте нет
      (Netcode/Lobby/Matchmaking отсутствуют), есть лишь пакет `com.unity.multiplayer.center` — удалить.
      Единственная онлайн-функция — **таблица лидеров** (асинхронная: отправка рекорда + чтение топа).
- [x] **Лидерборд — Firebase Auth (анонимный) + Firestore** (утверждено 2026-10-25).
      Почему не Google Play Games: к записи GPGS можно приложить лишь `scoreTag` ≤ 64 символа, а наш
      `BuildSnapshot` — до 64 int → просмотр билда игрока (`BuildViewerUI`) потерялся бы. Firestore хранит
      снимок целиком, существующий UI лидерборда переиспользуется, Firebase всё равно в стеке.
- [x] **Firebase-модули: Analytics + Crashlytics + Remote Config + Auth + Firestore.** Облачных сейвов нет.
- [x] **Addressables — только локальные группы** (всё внутри билда). Удалённый каталог требует хостинга
      (CDN), версионирования каталога и даёт выигрыш только при частых контент-апдейтах без релиза — для
      нас не нужен. Ценность Addressables здесь — загрузка/выгрузка по требованию (память на слабых телефонах).
      Переход на удалённый каталог позже возможен без переделки кода (меняется только профиль групп).
- [x] **Достижений на мобилках нет.** `AchievementManager` (Steam) живёт только в PC-сборке;
      на мобилках — `NullAchievementService`.
- [x] **Ветки (2026-10-25):** `mobile` — основная ветка мобильной разработки. Фича-ветки создаются от
      `mobile` и мержатся в `mobile`. `main` заморожена на последнем PC/Steam-состоянии и больше не
      трогается (никаких merge в обе стороны). Подробно — `docs/Git.md`.
- [x] **Сохранение забега (2026-11-02):** восстановление состояния боя, включая врагов, снаряды и эффекты,
      а не только билда или начала волны. Контракт снимка согласовать до миграции асинхронности и пулов.
- [x] **Анимации и частицы (2026-11-02):** желательно восстанавливать и визуальную фазу. Если замеры покажут
      заметные затраты производительности или памяти, косметическую точность допустимо снизить и пересоздавать
      визуалы. Игровые тайминги, урон и эффекты статусов восстанавливаются точно независимо от этого упрощения.
- [x] **Доступное тестирование (2026-11-02):** своего Android-телефона нет; основной рабочий цикл — Unity Editor.
      Способ проверки на реальных устройствах до релиза остаётся открытым. Codex отдельно записывает результаты
      Editor, PC Player, эмулятора и физического устройства.
- [x] **Цель FPS (выбор делегирован агенту, 2026-11-02):** 60 FPS на согласованном устройстве среднего уровня,
      режим 30 FPS для слабых устройств/экономии батареи. До аппаратных замеров это цель, а не подтверждённый результат.

- [x] **Android application ID (2026-11-05):** `com.havocstudioteam.ets` — выбран пользователем.

- [x] **Порядок работ с 2026-11-23 (выбор делегирован агенту).** Сначала — играбельная Android-сборка без
      правок `MainScene`: всё мобильное поведение собирается в рантайме (`Assets/Script/Mobile/`), чтобы ПК-ветки
      с правками сцены вливались без конфликта. Затем страховочные тесты и замеры. DI/UniTask/Addressables/Firebase —
      после первой проверки на устройстве: без телефона и Play Mode-тестов массовая миграция 332 обращений
      `.Instance` даёт риск регрессий и не меняет опыт игрока.
- [x] **Ветка порта (2026-11-23):** `feature/android-port` от `mobile` + влитая `feature/steam-lobby` (актуальная игра:
      баланс, экран победы, награда босса). Дуэль/лобби на телефоне скрыты — решение «только одиночная игра» в силе.
- [x] **Осмотр vs покупка на телефоне (делегировано агенту, 2026-11-23):** короткое касание слота магазина — покупка,
      как клик на ПК; удержание ≥0,35 с — тултип, отпускание после осмотра не покупает. Отдельное подтверждение
      покупки пока не вводится — пересмотреть после плейтеста на телефоне.
- [x] **Safe Area (2026-11-23):** `renderOutsideSafeArea = false` — Android рисует только в безопасной области,
      HUD не уходит под вырез без правки каждого Canvas. Canvas'ы на телефоне масштабируются в режиме Expand.
- [x] **Рекорды на телефоне до Фазы 12:** локальная таблица лучших забегов устройства со снимком билда
      (`LocalLeaderboardService`) вместо заглушки с выдуманными игроками.
- [x] **Распределение работы с 2026-11-23.** Codex принял этапы, которые раньше были упражнениями пользователя. VContainer, UniTask, пулинг, Addressables, New Input System, DOTween, Firebase и лидерборд остаются в плане.

## Принципы миграции
- Поэтапно сохранять рабочую PC-версию. Проверять компиляцию и консоль, использовать Play Mode или Player, обновлять RoadMap и фиксировать связанные изменения в Git. Рабочая ветка порта — `mobile`, состояние `main` остаётся замороженным.
- Вводить сборки и сервисы по мере появления проверенных границ. Враги, снаряды и эффекты получают зависимости при выдаче через фабрику или пул. Для Steam и Android использовать отдельные реализации платформенных интерфейсов.
- Замеры хранить в проекте с указанием сборки, платформы, качества и сценария. Действия на реальном устройстве вынесены в Фазы 9 и 13. При отсутствии телефона продолжаются независимые работы, статус аппаратных проверок сохраняется в плане.
- Условные оптимизации проверяются замерами. Если вариант отложен или не нужен, фиксировать основание и условие возврата к нему.

## Риски
- Разбиение на asmdef может затронуть зависимости импортированных ассетов. Выделять модули постепенно и после каждого изменения проверять PC и Android.

- Без измерений на телефоне нельзя подтвердить FPS, расход батареи или нагрев. Сохранить проверку реального устройства в плане релиза.

### Подтверждённые проблемы и риски
- **Блокер компиляции без Steam:** `Assets/Script/Steam/SteamManager.cs` — using UnityEngine находится

### Выполненное учебное действие — исправление пула перед baseline (2026-11-05)
- **Зачем было нужно:** свободный стек должен содержать только свободные объекты. Исходный Create клал новый объект
      в стек, а Get выдаёт его активным, оставляя там же. Следующий Get выдаёт его повторно; число врагов
      и снарядов оказывается неверным, поэтому такой baseline непригоден.
- **Твои шаги:** открой Assets/Script/PoolObject/ObjectPool.cs. По исходной нумерации замени строку 16
      `Create();` на `pool.Push(Create());`: Create возвращает неактивный объект, а Push кладёт его в свободный стек
      при предварительном заполнении. Затем удали строку 23 `pool.Push(obj);` из Create: при вызове из Get новый
      объект будет сразу выдан активным и не должен одновременно оставаться среди свободных. Get и Release не меняй.
- **Критерии:** два Get без Release дают разные активные объекты; initialSize=0/1/несколько работает;
      после Release объект снова можно получить. Агент проверит повторное использование и игровой smoke.
- **Что написать после правки:** «Я исправил ObjectPool.cs для фазы 0. Проверь код и подготовь сценарий baseline».
- **Дальше:** воспроизводимый сценарий поздней волны/босса → учебные замеры Profiler/Memory Profiler/Frame Debugger
